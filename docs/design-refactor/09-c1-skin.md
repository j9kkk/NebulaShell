# C1 换皮：深空冷调 · 克制（已落地）

> 批次：C1（换皮第一轮）。前置：B0–B6 token 层债务已清零。
> 结论：**采纳方向 A「深空冷调 · 克制」**，只改 token 值，组件选择器、布局、圆角档位、字号档位一律未动。

## 1. 为什么必须先做 A 而不是先调组件

换皮的问题从来不是「哪个颜色好看」，而是**同一份视觉决策散落在几十处组件规则里**。
B0–B6 把这件事收成了「一个 token 只在一个地方定义、组件只引用 token」之后，
换皮才变成「改 31 个值 → 全站跟着变」，且可以用运行时注入做 A/B（`ui:check inject`）。

## 2. 拍板过程

| 方向 | 内容 | 结果 |
|---|---|---|
| A 深空冷调·克制 | 保留 `--accent #5b8cff` 身份色；表面四级拉开；主按钮渐变压深；蓝/红/琥珀上的文字改深墨 | **采纳** |
| B 石墨中性·专业 | 去全屏蓝染、主按钮改实色、圆角整体收一档（10/8/12 → 8/6/10） | 未采纳：改动面更大，且纯中性灰在暗色里最容易退化成「发灰的灰布」——正是本轮要修的病 |

A/B 都通过了同一套客观体检（26 项全绿）；两轮独立截图复核给 B 的「层次干净」分略高（8.5 vs 8.0），
但 A 保住了品牌蓝且视觉面更小，最终按「身份优先 + 改动最小」采 A。
A 的首版表面台阶是 3.3/4.4 L\*，被复核判定「侧栏与主区容易融成一块」，已按结论拉到 4.8/6.0。

### 一次误判与纠正（写下来免得下次重犯）

首轮复核我给的提问是「蓝色主按钮文字是否清楚（**现在按钮上是深色字**）」——
把结论写进了问题里，模型顺着答「深色字发闷、建议改回白字」。
实测 `.btn.primary` 的 `color` 是 `rgb(255,255,255)`、`--btn-primary-text` 我根本没改；
把按钮裁图放大 2 倍再问，答「接近白色」。
**教训：视觉复核的提问不许带结论。**

同理，「辅助小字发灰」的说法也被数字否掉了：状态栏 7.22:1、10px 计数 6.33:1，
都在 AA 之上，属观感而非缺陷，不再提亮（继续提只会把层级压平）。
